## Completeness

- V23. Rule 1: a non-empty store needs its update.
- V24. `x_init` with fields and no `x_deriv` method is a build error.
- V25. `s_init` with fields and no `s_update` method is a build error.

- V27. The second is a discrete store nothing updates.
- V28. The framework will not silently supply `ẋ = 0`, which is a model, not a default.
- V29. An unupdated discrete store is a parameter in disguise; parameters are plain struct fields.
- V30. The didactic style says exactly that.
- V31. An empty store is a stateless leaf's tier marker and owes nothing.
- V32. `m_init` carries no such obligation.
- V33. Modes are written by handlers.
- V34. A component may legitimately declare modes no event of its own transitions.
- V35. Rule 2: an event needs both halves.

- V37. Method lookup catches it at declaration-reading time, rather than as a `MethodError` at first firing.
- V38. An event that fires only in a corner of the envelope would otherwise hide the omission indefinitely.
- V39. Rule 3: tier is declared by the store.
- V40. Every leaf declares `x_init` or `s_init`. [D-195, D-263]

- V42. So every leaf announces its tier in one place. [D-195, D-263]
- V43. A stateful leaf announces its tier in the update law as well: `x_deriv` beside `x_init`, `s_update` beside `s_init`.
- V44. The two output stages are one pair of names shared by both tiers, so they announce nothing and cast no vote. [D-220]
- V45. (bold) The remaining tier-implying declarations must agree. [D-112, D-249]
- V46. `m_init`, `state_events` and `x_projection` are continuous-only.

- V49. A `Pinned` entry in a contract is continuous-only.
- V50. Because the discrete tier pins wholesale and the marker there says nothing.

- V52. Every declaration takes the component alone. [D-263]
- V53. `ws_init` takes the scalar on both tiers. [D-263]
