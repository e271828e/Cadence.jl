# Part I — Foundations: conformance audit

Agent A. Slice: `docs/design/spec.md` lines 127–1590 (§1–§7). Repository at
`master`, tip `2c02afb`. Read-only pass; no Julia process was started and the
test suite was not run. `docs/design/implementation.md` was not opened.

## 1. Summary

Part I's *structural* obligations are in good shape and, in several places,
carried more precisely than the prose asks. The two-stage split, the bundle
law's `iff` shape on both the argument and the return side, the closed
per-function name sets, the one-home-per-datum rule, the flat continuous
buffer with build-time offsets, the per-eltype cell stores, the activation
walk, the one-level connection rule, single-connection fan-in with the
cross-level TwoProducers case, and the §5.3 boundary macro-sequence
(`integrate → project → [sweep → guards → handlers] → ticks`) all read as
faithful implementations that I could trace end to end. The §7.5 allocation
invariant is real and CI-tested at the `phase_bodies` seam, including the
guard-bearing quiet boundary.

The gaps cluster in three places, and all three are in the parts of the slice
the brief asked me to audit hardest.

**First, and largest: §5.6 is entirely unimplemented, and §5.5's diagnostic is
the shape D-012 explicitly rejects.** There is no feedthrough tracer of either
mode, no SCC decomposition, and no genuine/artificial classification.
`schedule_stage2` (`src/build.jl:219–252`) reports the *raw topological-sort
residue* as `AlgebraicCycle.members`, a list of component paths. D-012's
"Rejected" list names exactly that alternative — "*Naming the cycle by the
topological stall's raw residue:* over-reports — the residue holds the innocent
downstream cone" — so this is an unratified deviation, not a licensed
simplification. The residue is genuinely over-inclusive: any acyclic component
downstream of the cycle also fails to drain from `ready` and lands in
`members`. The message form is also wrong: component paths joined by `→`
(`"ctl → plant → sum"`), where §5.5/§5.6 specify port terminals in the
canonical slash form closing back on themselves
(`aero/F → dyn/a → aero/α̇ → aero/F`), and §5.4 specifies a message offering
*both* remedies with the offending stage-2 function in its own payload field.
The diagnostic's own docstring at `src/diagnostics.jl:580–582` claims SCC
semantics the code does not deliver.

**Second: auto-publication of state and mode fields does not exist.** §5.3's
"Rule. A declared output that matches a state or mode field by name and type,
and that no stage produces, is auto-published by the framework from the state
stores at stage-1 position" has no implementation. Worse, the build actively
*rejects* the case: `probe_stage2`'s completeness pass raises
`DeclaredNotProduced` for any declared port no stage returns
(`src/build.jl:534–540`). So the spec's mechanism is not merely absent, its
trigger condition is a build error. Nothing retires the obligation — D-169
(ratified, 2026) is written entirely around auto-published ports and depends
on their existence, and D-152's supersession by D-154 concerns the *re-decode*,
not publication. This is the finding I would raise second.

**Third: the port value vocabulary is narrower than §3.1/§4.1 promise.** Cells
are flattened by the §7.1 leaf walk into per-eltype numeric buffers
(`src/store.jl`), so a cell's type must decompose into `Real` leaves and
`SArray`s. An `@enum` type has no fields and is not `<: Real`, so
`leaf_types(MyEnum) == Type[]` and `cell_layout`'s `place!` refuses it as
`IllegalPortType` (`src/build.jl:278–284`). §3.1 explicitly wants
"mode-valued outputs" and the FSM-as-continuous-leaf factoring; §4.1 lists
"enums" among what a port may hold. The same walk breaks §4.4's bulk-data
field handle: a port type carrying a reference field (a heightmap `Matrix`, a
wind grid) is walked into its internal `MemoryRef`/`Ptr` fields by
`leaf_types`/`_reconstruct_expr`, which is not a representation those types
survive. §4.1's "immutability plus frozen references… `isbits` is the common
case, not the rule" is therefore not what the cell store implements. No
decision I found narrows the port vocabulary this way — D-162 adopts the
per-eltype store on compile-curve grounds and says nothing about the admissible
leaf set. Confidence medium-high: I read the walk carefully but did not run
Julia to confirm.

Two smaller items worth the coordinator's time: §5.2's `DeadStage` build error
for an empty `y = (;)` does not exist (D-194 re-affirms it after retiring `w`),
and §5.2's framing diagnostic for destructuring an absent bundle field — the
type-matched `FieldError` interception with did-you-mean against the legal set
— does not exist either; a body destructuring a store it does not own gets
Julia's bare error. §6.1's walk-compatibility clause and its
`WalkingFaceAtFrozenEntry` diagnostic are also absent, and the nominal bound
check is implemented as a structural `_accepts` match rather than the spec's
`<:`, which closes the door on §4.4's abstract input entry
(`terrain = AbstractTerrainField`).

Nothing in the slice defeated me. §5.6 and §7.4 were the two I spent least on:
§5.6 because it resolved to a clean absence, §7.4 because it is lineage and
asks nothing of the code.

## 4. Spec problems

- **§5.6 vs. `src/build.jl`: the spec asks for a large instrument that has not been built, and §5.5 depends on it for its message.** Either the tracer gets built or §5.5/§5.6 need re-scoping. The coordinator should note that D-012 is ratified and explicitly rejects the residue form the code currently ships, so "the spec is wrong here" is not available as a cheap resolution.
- **§5.3's auto-publication rule and §9.3's `DeclaredNotProduced` check are in direct tension.** As written, the same condition — a declared port no stage produces — triggers auto-publication in §5.3 and a build error in §9.3's completeness pass. The spec never orders the two. The code implements only the error. Whichever way it is resolved, §5.3 and §9.3 should say so explicitly.
- **§4.1's "immutability plus frozen references… `isbits` is the common case, not the rule" is not implementable as stated under D-162's cell store.** A flat per-eltype buffer requires the value to decompose into `Real` leaves. §4.1, §4.4's bulk-data handle pattern and §3.1's mode-valued outputs all assume a wider vocabulary than the representation the design later adopted. The code's shape is the honest one here; the spec should state the port-value vocabulary as explicitly as §7.1 states the state-leaf vocabulary, and §4.4's bulk-data paragraph should say what actually crosses a port.
- **§6.1's nominal bound check says `<:`, and `<:` is incompatible with the rest of the design.** The spec's own example of substitutability (§4.4's `terrain = AbstractTerrainField`) needs `<:`, but the cell layout needs a concrete declared type to size a cell, and D-166's embed-accept needs a structural per-leaf relation rather than a subtype one. The code chose structural matching and thereby closed §4.4's abstract entry without saying so. The design question — how a face is declared substitutable when the cell must be concretely typed — is unresolved in the spec.
- **§7.5's logging paragraph is stale.** "Records stored inline in a `Vector`" plus `sizehint!` predates D-023 (preallocated buffers rejected; the log retains the published snapshot objects themselves) and D-137 (progressive re-decimation under `log_max`). The paragraph should be rewritten against the mechanism the decisions settled; the guarantee it means to state — amortized-zero per boundary — survives unchanged.
- **§7.2 says "real leaves and `Real` type parameters following the scalar"; the code follows `Float64` positions only** (`retype`, `src/leaves.jl:185–189`). A state or port leaf deliberately written `Float32` would be silently pinned rather than walked. The code's reading is the one D-166 implies ("declarations are written at concrete `Float64`") and is probably the right one; §7.2's wording should be tightened to say `Float64` rather than "real".
- **§7.3 and `init_s`'s docstring disagree on the discrete state vocabulary** — "any immutable value… `isbits` is not required" against "any isbits type". The code enforces neither. Minor, but it is the kind of split that becomes a false finding later.
- **§5.2's `DeadStage` and §5.3's "a stage that would produce none"** are stated twice in slightly different words, and neither states what happens to a component all of whose stages are dead. Worth one sentence when the check is built.
