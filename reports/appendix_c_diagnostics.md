## 1. Summary

Appendix C names **78 kinds**. **66 exist** (65 `<: Diagnostic` structs plus
`StepError`, which is an `Exception` and correctly so). **12 do not exist at
all** — no struct, no site, no alternative spelling:
`WalkingFaceAtFrozenEntry`, `AbstractAtRoot`, `IllegalStateLeaf`,
`TierSignatureMismatch`, `MissingProbeValue`, `DeadStage`, `BundleFieldError`,
`UserCodeFraming`, `GridUtilization`, `DebtReanchor`, `ThreadBudget`,
`UnboundedRun`. Four of those twelve (`DebtReanchor`, `ThreadBudget`,
`UnboundedRun`, and by implication `GridUtilization`) are absent because the
*feature* is absent, and `dataplane.jl:36` says so in a comment. The other
eight are checks the build or the probe is specified to run and does not.

The reverse sweep is clean in the strict sense: **every `Diagnostic` subtype in
`src/` appears in Appendix C**, and `test_diagnostics.jl` enforces exactly that
(`Set(typeof.(occurrences)) == Set(subtypes(Diagnostic))`, line 492). The kind
set is genuinely closed. One user-visible exception type sits *outside* the set
by design (`InternalInvariant`, D-215); one more (`BuildError`) is the carrier
§13.2 specifies.

Every one of the 66 has a `severity`, a `path` and a `message` method — I
checked all 65 structs against the `message` methods and the sets match — and
`test_diagnostics.jl:236` "diagnostic kinds (§13.2, Appendix C, D-214, D-215)"
instantiates one occurrence of each and asserts the severity column verbatim.
Rendering is in the best shape of the four questions.

The three findings I would raise first:

1. **`ConformanceFailure`'s field-set diff is order-sensitive**, contradicting
   both its Appendix C payload column ("order-insensitive, the return having
   been canonicalized first") and **D-151**, which is ratified. `keys(ẋ) ===
   keys(x)` at `build.jl:1050` and `keys(x⁺) === keys(x)` at `build.jl:594`
   compare tuples of symbols by identity, so a component whose `f` returns
   `(; v, q)` against an `init_x` of `(; q, v)` is refused. `trim.jl` *does*
   canonicalize (`NamedTuple{RK}`, `NamedTuple{K}`); the stage/state seam does
   not. This is a behavioural defect wearing a correct kind name.
2. **Eleven build kinds Appendix C marks `collected` are thrown fail-fast**,
   one violation at a time, aborting the stratum before its siblings are found:
   `PathResolution`, `FaceDirectionConflict`, `UnknownFaceSelection`,
   `ClassMixed`, `ClassUnreadable`, `StoreWithoutUpdate`, `TierUnreadable`,
   `WireTypeMismatch`, `AlgebraicCycle`, `ProducedByTwoStages`, and the
   source/destination arms of `UnknownPort`. §13.1's whole argument is that
   these cluster in practice; the flatten pass collects its *own* refusals
   (`w.viol`, `assembly.jl:658`) but the endpoint-resolution helpers it calls
   throw through it. Two kinds go the other way: `UndeclaredReturnField` and
   `HandlerReturnKey` are marked `fail-fast` and collect.
3. **Thirteen `string(T)` sites render a user-authored binding type
   fully qualified**, bypassing `_typename` — `bindings.jl:140,144,158,163,166,
   173,181,184` and `roster.jl:80,82,84,86,88`. The same payload field
   (`BindingContractMismatch.binding`) is filled with `_typename(b)` at
   `roster.jl:51` and `:62`, so one kind renders its subject two different ways
   depending on which arm fires. `EventHalfMissing.found` and
   `ContainerMixed.types` store raw model types rather than names, which §13.2's
   "strings, never instances and never model types" rule forbids outside the
   port-type exception.

Payload shortfalls are the broad, low-grade problem: **21 existing kinds carry
less than their column names**. Most are one missing field, several of them the
list-in-hand that §13.2 makes doctrine (`TransparentContainerUnknown`,
`ClassUnreadable`, `TierUnreadable`, `IllegalPortType`, and most arms of
`ReadBindingUnresolved` and `TapResolution` — the last two flagged in their own
source comments as deliberate omissions citing `implementation.md`). Two are
structural: `AlgebraicCycle` carries neither the wires nor the classification
and names *components* where the spec asks for *terminals*, and
`ProducedByTwoStages` omits both stage names, which is the entire point of the
diagnostic.

No section defeated me. The one thing I could not settle cheaply is whether
`ConformanceFailure`'s missing `simulation time` field matters at runtime: it
reaches the catch site as a `StepError` species, and `StepError` carries `t`, so
the fact is present in the composite even though the kind lacks it. I marked
that `partial`, not `deviation`.

### Spec problems

- **D-151 and Appendix C's `ConformanceFailure` column disagree with the code, and the code is the one that is wrong.** D-151 (ratified) mandates canonicalization at every author↔framework NamedTuple seam; the trim seam does it, the stage/state seam does not. Either the code should canonicalize before `keys(…) === keys(…)`, or D-151 needs a carve-out naming the state seam. As written the appendix promises a behaviour no code delivers.
- **`UndeclaredReturnField` and `HandlerReturnKey` are marked `fail-fast` and the code collects.** `build.jl:153` argues the collecting case in one sentence ("a stage returning three wrong types names all three") and it is the better rule: these are per-field passes over a return already in hand, which is precisely §13.1's own definition of a collecting population. The appendix's policy column looks like the defect here, not the code.
- **`PathResolution`'s read-side arm may be unreachable by construction.** The column asks for "the field's declared type" when a read-side traversal passes a generically-held field; `assembly.jl:250` argues that D-207's one-level rule means an endpoint "stops before any field it could traverse past", so the generic-holding question never arises. If that reasoning holds, the column is specifying a payload for a case the design has since eliminated.
- **The per-writer runtime kinds are specified with a `device id` / `writer id` payload field that the channel's architecture makes redundant.** Six kinds (`OutOfClaimEntry`, `DeviceCrash`, `ReplayDiscardedStaging`, `MalformedDatum`, `EntryTypeMismatch`, and by symmetry `ClaimedFaceEntry`'s incumbent) name it; `dataplane.jl:38` argues the cell is per-writer so no call passes an id, and singles out `DeviceJoinTimeout`'s `who` as the one genuine payload subject. That reasoning is sound and the appendix should say so, because as written five rows read as unimplemented payloads when they are a deliberate architectural choice. **This is also the biggest single source of `partial` verdicts in my table**, so resolving it one way or the other would clean up six rows at once.
- **`InternalInvariant` is a user-reachable exception type outside the closed set, and Appendix C does not acknowledge it.** D-215 rules that internal invariants are not diagnostics, which is right, but the appendix presents itself as the acceptance-test contract for what a user can see thrown, and `InternalInvariant` (`diagnostics.jl:213`, thrown at eight sites — `build.jl:148,330,869`, `trace.jl:171`, `sim.jl:1066`, `assembly.jl:516`, `devices.jl:187`, `executor.jl:116`) can reach a user. A one-line note in the preamble would close the gap.
- **`AttachUnknownFace` and `ReadBindingUnresolved` are specified to carry "the device (by type)" but both fire from binding-level code that has no device in scope** (`roster.jl:206` is inside `_stake_claims` over a binding; `bindings.jl:158–184` is inside `_compile_gather(layout, nt, T)`). Either the column should say "the binding, by type" — which is what both carry and what the message reads better as — or the call sites need the device threaded through.
- **`StopFaceInvalid`'s "binding site (constructor or `run!`)" has grown a third site.** `_stop_faces` is also called from `replay!` (`sim.jl:754`). If the field is added, its vocabulary is three values, not two.
- **`ArgumentInvalid`'s call vocabulary in the appendix (`step!`, `trim!`, `TableBinding`, a period constructor) is narrower than the code's** (`Period`, `Hz`, `Absolute`, `step!`, `run!`, `replay!`, `live!`, `trim!`, `trace`, `TableBinding`, `selector`). D-215 ratified the kind but not the widened vocabulary; the appendix row should be updated to match, since it is the acceptance-test contract.
- **The `raised` column for `ConformanceFailure` and `BundleFieldError` reads "build, at probe; runtime thereafter", but `BundleFieldError` does not exist and `ConformanceFailure` has no runtime site either** (grep: no `ConformanceFailure` outside `build.jl`). The appendix's own worked example of a two-stage raise is currently a one-stage kind and a missing one.
