## 1. Summary

Part IV divides cleanly into a well-built two thirds and one absent third.
§13.1–§13.6 and §14.1–§14.8 are implemented closely, often to the paragraph:
the collecting register, the one carrier, the execution cursor, the single
catch site, the nonfinite sweep at the boundary's first act, the four
termination sources with their consultation order, the one-tail-two-entries
shutdown, the four condition node kinds with provenance, the two application
registers over one plan, boundary zero with the D-205 amendment, root-input
totality, and the trim service end to end including the Levenberg–Marquardt
backend, the two-half scratch world of D-213, the service-owned verdict and
the `TrimReport`. Several of these read as *better* than the spec; the
condition algebra in particular.

The absent third is §14.9 mounting and §14.10 linearization, plus §13.7's
library. **Neither `at(prefix, ::TrimProblem)` nor `at(prefix, ::Reads)`
exists**, so a trim problem is not relocatable and the five-line lift the
spec spells out is unwritten. **Linearization does not exist at all** — no
`linearize`, no tap lists, no seeded Jacobian pass, no `LinearizedSS`, no
`design_world`. The selector family they are built from is complete and
correct, so the gap is the service, not its vocabulary. No decision in
`decisions.md` ratifies either absence; D-071 and D-108 both *assume* them.

The three findings I would raise first, other than those two:

1. **§13.3's register scoping is one register, not three.** `resolve` /
   `resolve_terminal` (`assembly.jl:255,306,322`) implement the structural
   register verbatim and nothing else. The load-bearing clients (condition
   entries, trim `reads`) and the diagnostic clients do not go through them at
   all: they do an exact-match lookup into the compiled `flat.paths` list
   (`conditions.jl:397`, `readers.jl:257`). Consequently **the generic-holding
   rule is nowhere implemented** — no site anywhere in `src/` tests a declared
   field type for concreteness — and §13.3's central claim ("client policy
   rides on one primitive", D-083/D-130 carried into resolution) is not what
   the code does.
2. **§13.2's recognized `FieldError` class is absent.** `BundleFieldError`
   does not exist as a struct or a name anywhere in `src/`. There is also no
   framing diagnostic for a user-code throw at build: `build.jl` contains no
   `try`, so a probe that throws propagates raw, without component path,
   function or probe context, and without becoming a `cause`. Both halves of
   §13.2's "user-code exception" paragraph are therefore unimplemented.
3. **§13.4's typed conformance failure at runtime does not exist.** Every
   `ConformanceFailure` construction site is in `build.jl`; the runtime write
   is a bare `scatter_group!` with `getfield` (`store.jl:81`), so a stage
   returning the wrong field set at runtime raises a plain `FieldError` that
   reaches the catch site as an untyped `cause`, not "a species of `StepError`
   carrying the field-diff payload".

No section defeated me. §13.7's standard component library and `Build`
provenance printer are absent but the spec itself frames the library as "a
migration-phase deliverable", so I have graded it accordingly and flagged the
printer separately.

### Spec problems

1. **§13.1's barrier granularity is ambiguous.** "A stratum that produced any error-severity diagnostic … throws before the next stratum begins" can be read as "collect across the whole stratum, then throw" or "do not cross the stratum boundary with errors outstanding". The code takes the second reading and throws per pass. The first reading is what "each returns its full violation list" and the compiler-style rendering suggest. The spec should say which, because the difference is user-visible: whether an unwired input and a bad `sample_times` in the same stratum report together.
2. **§14.7 and §14.8 disagree on the kind for an unknown `reads` selector.** Line 8253 (§14.7) makes "an unknown `reads` selector" one of the `TrimProblemInvalid` malformed cases; line 8481 (§14.8) says the error is "collected, mirroring linearization's `TapResolution`". The code splices `TapResolution` values into the `TrimProblemInvalid` throw, which satisfies neither reading cleanly and is arguably better than both — one throw, each half wearing its own kind. Worth ratifying the code's shape.
3. **§13.2's warning taxonomy has three streams and the code has four emitters.** Build (empty), runtime cells, service per-call annotation. `EmptyGreedyClaim` is an attach-time `@warn` that belongs to none of them: it is not collected into a `BuildError`, it is not in a diagnostic cell, and `attach!` is not a stopped-sim *service* call in the §14 sense. Either the "service warning" category should be widened to "synchronous per-call annotation" generally, or §11.3 should say which stream attach-time warnings ride.
4. **§13.3's register table and the code's shape disagree, and the code may be right.** The spec's "client policy rides on one primitive" is elegant but the load-bearing and diagnostic registers do not actually need a *tree walk*: by the time they run, the build has a flat list of absolute paths, and an exact-match lookup is both cheaper and exactly as correct for a concrete build. The generic-holding rule is the one thing that genuinely needs the declared-field walk, and it is the one thing the code omits. The spec should decide whether the generic-holding rule is load-bearing enough to justify a second walk over `resolve`'s.
5. **§13.4's disposition rule conditions the rethrow on the "unattended run" register, and the code does not.** The spec's distinction — unattended rethrows, interactive logs — presumes a way to tell them apart at the catch. `run!` blocks its caller in both registers, so the distinction is not observable at that point without a deployment flag. The code's unconditional rethrow is simpler and arguably correct; the spec should either drop the split or name the flag.
6. **§13.2's "strings, never instances" doctrine has no stated exception for authored *values*.** `ConditionResolution` and `TrimProblemInvalid` must show the offending value to be didactic ("the authored value is `…` which does not convert"), and that value is a user instance. The doctrine's carve-out currently covers port *types* only. Either the carve-out should be widened to "the offending value at a conversion refusal", or the kinds should carry a pre-rendered `String`.
7. **§14.10's tap-side discrete rejection has no counterpart in the read register, and the spec does not say whether it should.** `get_state` on a discrete component is legal for trim `reads` (§14.7 validates against `init_x`/`init_s`, both) and illegal as an `x` tap (§14.10, D-167/D-197). One selector, two legalities, decided by the client — which is fine, but §14.4's "a selector resolves against a source, before any client policy applies" makes it sound like the source decides. Worth a sentence.
