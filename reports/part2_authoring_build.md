Agent B. Repository tip `2c02afb`. Slice: §8 (the declaration layer) and §9
(the build pipeline). Primary code read in full: `declare.jl`, `assembly.jl`,
`build.jl`, `store.jl`, `executor.jl`, `leaves.jl`; read selectively:
`trim.jl`, `sim.jl` (the constructor and `phase_bodies`), `diagnostics.jl`
(kind list and the payloads of the kinds this slice names).

One Julia process was started, for three questions the source could not settle

quoted verbatim in the rows they belong to.

## 1. Summary

§8 is in very good shape and §9 is in good shape structurally, but the two
sections fail in opposite directions and the failures are not the same species.
§8's declaration surface is essentially complete and often more careful than the
spec: every name in the inventory exists with the right arity, the tier
classifier reads the whole name family, the class rule is total, the container
and name-transparency machinery is implemented down to the three-arm collision
family, the rate fold is the spec's table line for line, and the §8.8
passthrough pair matches the spec's sketched signature keyword for keyword. What
is missing from §8 is missing at the edges — abstract entries, the fan-out
tolerance meet, containers of containers, the shadowing check.

§9's pipeline is present and correctly ordered, but three obligations the spec
treats as load-bearing are absent, and they are the findings I would raise
first.

**First, the always-on conformance check (§9.5) does not exist.** The probe half
is implemented well — `_check_ports`, `_accepts`, `_embed`, `_pin_hint`, the
handler key-by-key law, the guard form check. But the executor's store site
(`executor.jl:143-147`) is a bare `scatter_group!` with no expected type, no
`isa` test and no diff. `scatter!` is `@generated` off the *declared* type and
assigns leaves into a typed buffer, so a divergent branch returning the wrong
scalar is silently converted. Verified: scattering `3::Int` into a `Float64`
cell stores `3.0` with no complaint. Everything the spec hangs on that check —
§8.1's "at first execution otherwise" clause, §8.3's branch-shape rule, §8.4's
forgotten-branch walkthrough, §9.3's "the always-on check remains the
completeness backstop" — is therefore undischarged.

**Second, the two wiring type clauses are not Stratum A checks.** §9.1 lists the
nominal bound check and the tier-scoped walk-compatibility clause among Stratum
A's resolution checks, decidable by evaluating both declarations at a marker
scalar with no user code. Neither exists. `flatten` performs no type comparison
at all. What stands in their place is `_probe_input` (`build.jl:1028-1042`),
which compares the entry against the *observed value's* type at probe time, one
stratum later and after user stage code has run. The practical consequences:
`WalkingFaceAtFrozenEntry` has no implementation and no struct; abstract entries
(`terrain = AbstractTerrainField`, §8.2's demonstrated field-handle client) are
rejected by `_accepts` for every producer; `AbstractAtRoot` does not exist.

**Third, auto-publication is absent, and with it the D-168 fan-out meet.**
`probe_stage2`'s completeness pass errors `DeclaredNotProduced` for any declared
port no stage returned, so §5.3/§8.3's auto-published state and mode names are
a build error rather than a framework write; the diagnostic also lacks the
state-field list §8.3 requires it to hold ("not produced by any stage and not a
state field"). Separately, `_root_input_type` takes `first(declared)` instead of
the meet, so the spec's own example of a legitimate model — one root input
consumed by a promoting leaf and by an AD-opaque `Float64`-entry leaf — builds
at nominal and then refuses its `Dual` activation. Verified: the mixed-tolerance
fan-out throws `WireTypeMismatch: 'b'.u declared Float64, fed from root input
'in'::Dual — if this leaf participates in differentiation, declare it 'T'`,
which is the one message that is certainly wrong here, the author having
declared `Float64` on purpose.

Two smaller absences worth naming: the §7.1 closed-leaf-vocabulary check on
`init_x` that §9.1 assigns to Stratum A does not exist (verified: an
`init_x = (n = 1, q = 0.0)` builds, and its `Dual` activation builds too, with
an `Int` living in the flat buffer), and §9.2's whole printable register — the
hyperperiod chart, the anchor/component tables' rendering, the leave-one-out
refinement factors, prime attribution, `GridUtilization` — is unimplemented;
there is no `show` method anywhere in `src/` outside `showerror`.

No section defeated me. The one place I am least sure of is §9.2's "printable
data": the *data* is all there on `Flat` and `Build`, and how much of the
printing the spec actually mandates is a judgment call I have made
conservatively (`partial`, not `pending`).

## 3. Two lists

### Observed outside my slice

- `src/Cadence.jl` has **no `export` statement**; every public name is reached as `Cadence.x`. Appendix B's exportedness column (Agent G) and §16's periphery surface are both affected.
- No `Base.show` method exists anywhere in `src/` except two `showerror`s. Every "printable artifact" in the spec — the bound schedule, the face table, snapshots, `TrimReport`, the roster — renders as the default Julia dump.
- `UserCodeFraming` (§13.1) has no struct and no wrapping `try` at any probe or runtime user-code call site.
- Auto-publication (§5.3) is absent framework-wide, not only at §8.3's conformance rule; the spec's own worked `Engine` (spec 1799: `ω` in `output_types`, produced by no stage) would not build.
- §4.4's field handles / bulk-data handles have no implementation; nothing in `src/` or `test/` declares an abstract-typed input entry.
- `Flat.comps` is `Vector{Any}` and `Layout.addr` a `Dict{…,Any}`; both are build-time only, but they mean the `Build` is not concretely typed (relevant to §9.2's immutable-shareable-artifact claim only in spirit).
- `_check_state_write` and `_check_derivative` both use `nleaves` equality as their per-field type predicate; the same weakening shows up in `project` (§5.3, Agent A) as in `f` (§9.5, mine).
- `ExecutionCursor` (§13.4, Agent E) is threaded through every entry constructor in `compile` and written on every dispatch; I saw no path where it is *not* written, which is the property §13.4 wants.

### Spec problems

- **§8.5's `Group` sketch omits rate declarations, and the implementation is better.** The spec's four-field `Group` cannot carry a `sample_times` declaration, so an ad-hoc topology with a subsampled child is unspellable; the code adds a `rates` field and a `sample_times(g::Group)` method. But this collides head-on with §8.7's "the declaration belongs to the assembly type, not to the child instance" and with D-042's rejection of instance-carried rates. One of the two texts should move. The code's position (a `Group` is an anonymous *type*, so its instance data is its type-level declaration) is defensible and should be written down.
- **§8.2's bound check is stated over `<:`, and `<:` cannot be what the design wants for a struct-valued port.** `Float64` vs `Float64` degenerates to equality as the spec says, but `GearContact{Float64}` vs `GearContact{T}` at an activation needs the per-leaf structural comparison `_accepts` actually implements. The spec's "one uniform rule, degenerating to exact equality for a concrete entry" is true only for scalar leaves.
- **§9.5's "canonicalizing reorder" is a no-op given §4.3's named scatter.** The executor writes each returned field into its own named cell, so field order is already irrelevant; the spec spends a paragraph on a `NamedTuple{names(Expected)}(y2)` reorder that the name-keyed scatter makes unnecessary. Worth simplifying to "the check is over the name set and the per-name types" rather than prescribing a reorder.
- **§8.3's "declared but not produced" error and §5.3's auto-publication are in tension as written.** §8.3 says the error names "both lists in hand", which presupposes auto-publication exists; §8.2's `Engine` example relies on it (`ω`); §9.1's Stratum B classification lists it as a third port class. Whichever way this is resolved, three sections move together, and a reader auditing only §8.3 cannot tell that.
- **§9.3's `probe_value` fallback list omits `StaticArray`, which the implementation needed.** `SVector{3, Float64}()` is not a valid zero-argument construction, so the spec's four-method list (`Real`, `Bool`, enums, `T()`) does not cover the most common non-scalar port type in the design's own vocabulary. `declare.jl:330` adds `zero(P)` for it. The spec's list should say so.
- **§9.1's "collected" deployment validation is not achievable in one barrier as the spec lists it.** Two of the eight violations (`h` nonpositive, `n < 1`) are preconditions of the grid arithmetic that produces the other six, so a single collecting pass would have to run the arithmetic on values it just rejected. The implementation's two barriers are the honest shape; the spec should either split the list or say the barriers are two.
- **§9.4 names `ProbeDual` as "the framework's exported canonical probe scalar" and gives its definition, but no section obliges anything to *use* it.** With `activations` taking any tuple of scalars and each service owning its own tag (`TrimTag`), the canonical scalar's only role is the CI idiom. Either the CI policy should be normative machinery (a `check` entry, as §9.4 parenthetically suggests) or `ProbeDual` should be described as a convenience constant.
- **§9.2's hyperperiod chart has no stated guard threshold.** "A guard for absurd hyperperiods" is the whole specification; an implementer has to invent the bound, and two implementations will disagree about when a model becomes unprintable.
