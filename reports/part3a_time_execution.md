## 1. Summary

§10.1 through §10.6 are implemented closely, and in the two places the brief
flagged — the localization arithmetic of §10.4 and the tick gate of §10.5 —
the arithmetic is right, not merely present. The ITP iteration in
`localization.jl:185–212` is a faithful Oliveira–Takahashi ITP over the unit
θ-bracket (κ₁ = 0.2, κ₂ = 2, n₀ = 1, ε = tol/2, `nmax = ceil(-log₂ tol) + 1`,
`r = ε·2^(nmax−j) − (hi−lo)/2`), it is entered only past a *measured* σ₀ < 0,
and it returns `hi`, the holding endpoint, so §10.4's "`t* = tₙ` is
structurally impossible" holds by construction rather than by clamping. The
cubic Hermite in `stepper.jl:122–133` has the correct basis with derivatives
scaled by the segment width. The gate `(tick − Φ) % D == 0` in
`executor.jl:358–365` is computed over the *base-tick* index (`k ÷ n`), not the
frame index, which is the correct quantity; the affine fold `(a, K·m, c + φ·m)`
in `assembly.jl:606–614` and the base-tick resolution `D = m·D_a`,
`Φ = Φ_a + c·D_a` in `build.jl:777–791` compose exactly as §10.5 states, and
the canonical residue survives.

**§10.7 is absent in its entirety.** There is no pacer, no wall-clock map, no
deadline, no debt, no `p`, no `margin`, no sleep-then-spin, and no pacer entry
in the published framework status. `Simulation` has no pacing keyword and
`run!` never waits. `dataplane.jl:8` and `:36` record the absence as
deliberate and point at `implementation.md`, but **no decision in
`decisions.md` defers or narrows §10.7** — D-021 remains ratified and D-133
still fixes `margin = 2 ms` and the `5·h/p` forgiveness threshold as
spec-owned constants. This also makes §10.1 partial: five of its six loop
activities are framework code, the sixth does not exist.

The three findings I would raise first, after the pacer:

1. **`localization_tol` is measured against the segment, not the frame**
   (`localization.jl:195`). The stopping test is `hi − lo > tol` in θ over the
   current segment `h′`, so on a remainder step after a `t*` the effective
   width is `tol·h′`, not §10.4's and D-133's `tol·h`. Tighter, never looser,
   so it is a cost deviation rather than a correctness one — but it is
   unratified and the code's own docstring flags the substitution.
2. **A `ChatteringBudget` warning can be emitted for an edge that would not
   have localized anyway** (`localization.jl:72–82`). The budget gate sits
   *before* the θ = 0 validation, so once the budget is spent an
   epoch-caused edge — which §10.4 says "warns nothing" and "consumes no
   budget" — is reported as chattering. The state and the firing are still
   correct; only the diagnostic is spurious.
3. **§10.6's `firing_budget` warning fires one edge early relative to the
   spec's wording** — in fact it is exactly right, but the payload's fifth
   field is the count at exhaustion, always equal to `budget`, so the spec's
   "the exhausted budget beside the boundary's firing count" carries no
   information in the second slot. Cosmetic; recorded so the verifier does not
   re-derive it.

Nothing in §10.2–§10.6 defeated me. §10.7 defeated nothing; it is simply not
there.

### Spec problems

1. **§10.4 (3747–3751) calls tick eligibility a frame property; §10.5 (4092) keys the gate to the tick index.** With `Δt_base = n·h`, `n > 1`, these are different quantities and only the second is implementable. The code uses the tick index (`sim.jl:1033`) and is right; the spec's §10.4 bullet and §10.5's "the due set is the gate's image of the frame index" (4136) should both say *tick* index, and §10.5 should say explicitly what a non-tick frame top does — the code treats it exactly like a `t*` boundary, which is the only sensible reading but is never stated.
2. **D-133 spells the localization budget `event_budget`; §10.4 and the code spell it `localization_budget`.** The decision is stale against its own spec section. Worth reconciling so a reader grepping `D-133` does not conclude the keyword is missing.
3. **§10.4 (3918–3921) says the bracket is measured against `h`, and the spec's own sketch at 3852 writes the comparison as `(hi − lo)·h vs. tol·h`.** On a remainder segment there is no `h` — there is only `h′` — and the spec never says which. The code's choice (the segment) is arguably the better one, since the interpolant it is resolving is the segment's; but the spec should pick, because the two differ by up to a factor of the number of localizations in the frame.
4. **§10.4's budget-exhaustion prose (4030–4036) and its epoch-caused-edge prose (3886–3891) conflict on ordering.** The former says localization stops on exhaustion; the latter says an epoch-caused edge warns nothing and consumes no budget. Whether exhaustion is tested before or after the θ = 0 validation decides which wins, and the spec does not say. The code tests first, and warns.
5. **§10.6 (4552–4553) asks the `FiringBudget` warning to carry "the exhausted budget beside the boundary's firing count".** At the only site where exhaustion can be observed those two are equal by construction, so one of them is dead payload. The spec probably means the count *including* the suppressed edges, which nothing tracks.
6. **§10.5 (4126–4128) states the due set is "computed once for the boundary and reused".** The code recomputes the gate per round, which is cheaper than materializing a set and produces the same image. The spec is over-specifying an implementation where it means to state an invariant ("a due component is at its tick instant for the whole boundary"). The invariant is the part worth binding.
7. **§10.7 fixes `margin`, the debt threshold and the wait primitive down to measured microseconds, and none of it is built.** Given the section is otherwise the most operationally detailed in Part III, the gap between the spec's confidence and the code's silence is the largest single mismatch in this slice, and it is not recorded in the decisions log at all.
